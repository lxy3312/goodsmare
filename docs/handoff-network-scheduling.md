## 本次已实现

### 1. 关注调度与错误冷却

- `config.py`：关注新增 `priority`，支持 `high / normal / low`，权重分别为 `2 / 1 / 0.5`，默认 normal。
- `monitor.py`：`watch_periods()` 按原有理论请求预算分配目标周期；`_pick_watch()` 按逾期比例调度，避免低优先级长期轮不到。目标周期不等于实测完成间隔。
- 扫描、网页预览、测试搜索和 CLI 搜索共用 `Monitor.search()`，在同站锁内执行间隔等待、路由和错误冷却。
- “立即扫描”使用待扫描标记，不再清空真实扫描时间或网站冷却；修改一个关注只触发相关关注。
- 冷却保存在现有数据库 `kv` 表的 `monitor_cooldowns` 中，重启后恢复；尊重 `Retry-After`，登录失效时暂停对应网站，登录恢复不覆盖尚未结束的其他限流期。
- 请求间隔随机系数从 `0.8–1.3` 改为 `1.0–1.3`，避免实际等待短于设定下限。
- 修复汇率失败后反复请求的问题；推送上下文使用缓存汇率，避免发通知时等待汇率网络请求。

### 2. 推送延迟

- 新配置 `push_mode`：`instant`（默认即时）、`priority`（重点即时，其余合并）、`batch`（合并）。
- 合并发送保留 3 秒静默窗口、最长 12 秒等待。
- 新增 `dispatch.py`：每个渠道各自排队，同一渠道串行，不同渠道独立发送；记录待发送数、失败数、成功发送延迟。
- `notify.send_all()` 支持不同渠道并行；正常停止时等待队列发完。
- 重要限制：这是内存队列，不是持久化 outbox。失败只记录日志；原有 feed/去重记录先于实际发送写入，不能承诺崩溃或投递失败后自动补发。

### 3. HTTP 连接与线路

- 新增 `transport.py`：基于标准库 `http.client` 与 `urllib` 的 HTTP/1.1 连接池，没有新增第三方依赖。
- 支持 HTTPS、HTTP 代理 CONNECT、CookieJar 隔离、跳转、gzip 和 HTTP 错误响应；保留证书校验。
- 连接池按目标、代理、代理认证、CookieJar 等隔离；空闲 TTL 30 秒，总空闲上限 32、单键空闲上限 4。切换网络设置或重置连接会淘汰旧连接。
- `net.configure(cfg)` 统一应用全局代理及 `network` 设置；网站搜索通过 `net.route(source_key)` 指定线路组。
- `network.keepalive` 默认 true，`connect_timeout` 默认 8 秒，`read_timeout` 默认 20 秒；显式请求 timeout 仍作为上限。
- `network.routes` 支持各网站及 `domestic_push / overseas_push`：`inherit`、`direct` 或带端口的 HTTP 代理 URL。
- 已知国内推送域名默认直连；闲鱼固定直连；其他网站默认跟随原全局/系统代理。未知或自建推送域名默认跟随全局。
- GET/HEAD/OPTIONS 默认最多重试一次；POST 默认不自动重发，减少已被服务端受理后的重复通知。煤炉搜索是只读 POST，显式保留一次重试。
- 429、验证页和带 `Retry-After` 的失败不立即重发；证书校验失败不重试。

### 4. 后台、API、文档

- 关注编辑加入优先级；设置页加入推送模式、连接复用、连接/响应超时、分站线路、网络耗时和重置连接按钮。
- `/api/state` 新增 `monitor.timing` 和 `net.performance`；新增 `POST /api/network/reset`，清空连接和网络统计，不清除网站冷却。
- 网络统计按组保留最近 100 次逻辑请求的耗时、复用率、错误数；代理统计不显示账号密码。
- 分阶段耗时来自最终响应，整次 elapsed 包含重试/跳转等开销。这里不是实际 HTTP 请求数/分钟计数器，不能据此证明 128 次/分钟。
- 页面能识别旧后端尚未重启的情况，提示重启并禁用新网络设置，防止出现保存成功但实际未生效的误解。
- `migrate.py` 支持迁移 `push_mode` 和 `network`；更新 README、使用指南及相关测试。

## 尚未实现与后续讨论

- 没有新增类目轮询、`browse(category_id)`、共享类目列表分流、翻页补漏或定期关键词兜底。
- 没有多 IP 分片、代理自动轮换、自适应轮询间隔；没有在手机上配置官方通知。
- 用户提出的“全站 128 次/分钟、单关注 30 秒”目前作为方案比较基线，尚未以完整请求计数和逐关注间隔采样验证。
- 当前仍是各关注独立关键词搜索。`passes()` 只检查价格、must/exclude，不检查主关键词；这是现有关键词搜索路径的设计，不能原样用于类目列表。
- 配置检查发现 3 个关注没有 must，2 个关注启用了降价提醒。类目试点需要处理误匹配、旧商品降价、错类商品和最新一页被挤出的情况。
- 建议后续仅做煤炉试点：显式选择类目及参与关注，保留开关、共同预算、冷却和关键词兜底，并记录两路命中差异和页面覆盖。
- 理论账：10 个关注、1 个类目每 10 秒请求一次，加每关注 5 分钟一次兜底，是 `6 + 10/5 = 8` 次/分钟。若煤炉原为 20 次/分钟，只改煤炉则全站基线 `128 -> 116`。
- 上述 8 次/分钟要求类目周期与同站最小间隔分开，兜底错峰执行。若所有同站请求都严格至少隔 10 秒，总计最多 6 次/分钟，扣除兜底后类目不能仍保持每 10 秒扫描一次。
- 5 分钟兜底不能承诺近乎零漏检；只跑一天没观测到漏项也不能证明完整覆盖。先验证固定周期的类目试点，再评估自适应间隔。
